# ADR-0002：长度前缀二进制协议

- 状态：已通过
- 日期：2026-11-07
- 相关：`docs/protocol.md`

## 背景

TCP 是字节流：一次 `send` 可能被拆成多次 `recv`，多次 `send` 也可能被合并成一次
`recv`。应用层必须自己定义"一条消息到哪里结束"，否则收到 `hello` 却不知道下一
个字节是新消息还是这条消息的一部分。

需要选一种边界表示法，并决定字段的序列化方式。

## 候选方案

### A. 文本行协议（IRC 风格）

```
MSG #lobby hello world\r\n
```

**优点**：`nc` 或 `telnet` 可以直接手打调试；人类可读；抓包一眼看懂。

**缺点**：

- payload 里的换行必须转义，否则消息被截断
- 每条消息要逐字节扫描找 `\r\n`，复杂度 O(n)
- 二进制数据（将来的文件传输）几乎不可用
- 没有强制长度上限，恶意的长行就能吃满内存

### B. 长度前缀 + 类型字节 + 长度前缀字段

```
[4B len][1B type][2B field_len][field]...
```

**优点**：

- 边界 O(1) 判定，且**永不误判**（payload 里出现任何字节都无影响）
- 天然有长度上限，可以拒绝超长帧
- 类型字节让协议可扩展，不需要解析文本命令
- 二进制 payload 无障碍

**缺点**：

- 不能用 `nc` 手打，需要一个客户端工具
- 抓包需要工具解析

## 决策

采用 **B**，并写一个 `tools/chat_cli` 作为调试客户端。

理由的权重：

1. **正确性 > 便利性**。行协议的转义 bug 是经典事故源，长度前缀从结构上消除它。
2. 长度上限是安全边界，不是可选项。
3. 抓包困难由工具解决，成本一次性；协议本身的问题会持续存在。

## 后果

**收益**

- 粘包/半包处理变成"读头 → 判断够不够"，逻辑简单且可穷举测试
- 加新命令只加类型值，不改解析器
- 为 M8 的 WebSocket 复用同一套 Frame 语义（只是换传输编码）

**代价**

- 需要一个 CLI 客户端（M7 交付，同时用于集成测试）
- 协议演进必须遵守"只追加"规则，否则旧客户端会错位

## 补充：为什么不用 JSON

JSON 解决的是"结构化数据的可读性"，这里的问题是"消息边界"。用 JSON 仍然需要
自己定边界（通常还是长度前缀或换行），只多了一层解析开销和第三方依赖，对学习
协议设计反而是噪声。

JSON 适合配置和 API 响应，不适合高频的小消息帧。
