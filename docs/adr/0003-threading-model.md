# ADR-0003：线程模型（IO 线程 + 工作线程池）

- 状态：已通过
- 日期：2026-11-07
- 相关：`feat/thread-pool`

## 背景

M2–M5 的实现是单线程 reactor：一个循环里做 epoll_wait、recv、协议解析、
业务处理、send。

它足够跑几千个连接（实测 200 连接 438k msg/s），但有两个现实问题：

1. **业务变慢会拖垮 I/O**。一旦某条消息的处理需要磁盘、数据库或者复杂计算，
   整个事件循环就停在那里，所有连接一起卡住。
2. **无法利用多核**。无论机器有 8 核还是 64 核，只有一个核在工作。

## 候选方案

### A. thread-per-connection（阻塞 I/O，一连接一线程）

实现最简单，也是很多人第一次写服务端的做法。

**否决理由**：Linux 默认线程栈 8MB，1 万连接 = 80GB 虚拟内存。且线程切换在
高并发下开销巨大。这个方案在连接数上百时就开始劣化。

### B. SO_REUSEPORT + 多个 reactor 进程/线程

每个线程跑独立 epoll，内核把新连接分给其中一个。

**暂不采用**：共享状态（房间、用户表）要么放共享内存，要么放独立服务，
复杂度陡增。等真有单核打满的证据再说。

### C. 单 reactor + 工作线程池（本项目采用）

IO 线程只管 I/O，业务丢给线程池，结果经队列 + eventfd 回到 IO 线程。

### D. 保持单线程

**也保留了**：`--workers 0` 就是这条路。小规模部署下它最简单、最可预测、
没有锁竞争。不要因为"多线程听起来高级"就上多线程。

## 决策

实现 C，并把 D 作为可选项保留，用于对比和排错。

## 两条铁律

1. **Connection / fd / 映射表只在 IO 线程里碰。**
   工作线程拿到的是 `(SessionId, Frame)` 这样的值，绝不是指针。
2. **ChatHub 只被工作线程访问，用一把粗粒度 mutex 保护。**

违反第 1 条就会出现"一个线程在 send、另一个线程在 close"的经典 use-after-close；
违反第 2 条会出现数据竞争，而且往往只在压测时才暴露。

## 为什么用 eventfd 而不是轮询

工作线程把结果放进队列后，IO 线程还阻塞在 `epoll_wait` 里，没人告诉它"有新结果"。

- 轮询（每 10ms 醒一次）：延迟 + 空转，CPU 白烧
- 管道：两个 fd，读写各一，还要处理 EOF
- **eventfd**：一个 fd、一个 8 字节计数器，写一次就变可读，epoll 立刻返回

## 后果

**收益**

- 业务变慢不再阻塞 I/O
- 可以用多核
- 拿到一个可以讲清楚"为什么这样设计"的线程模型

**代价**

- 多了一把锁和一次队列往返
- 结果回投有微小延迟（一次 eventfd 唤醒）
- 调试变难：`gdb` 里多线程断点、日志交错

**验证方式**

- TSan 构建（`-DCHATROOM_TSAN=ON`）跑全部测试
- 集成测试里专门有一个 `WorksWithWorkerThreads` 用例覆盖这条路径
