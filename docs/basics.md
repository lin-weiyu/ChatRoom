# 读代码前需要知道的系统调用常识

这份文档解释 `fd`、`recv`、`EAGAIN` 这类词。它们是操作系统的基本概念，
不属于本项目——**所以放在文档里，而不是写进代码注释**。

读懂这一页，整个 `net/` 目录就通了大半。

---

## 1. fd 是什么

**文件描述符就是一个整数。**

你在程序里拿到的不是 socket 对象本身，而是一个号码：

```
你的程序                          内核
─────────────────────────────────────────────
int fd = socket(...);  ────►   文件表[3] = { 类型: socket,
                                 ├─ 接收缓冲区: [...]
                                 ├─ 发送缓冲区: [...]
                                 └─ 状态: 已连接 }
    得到数字 3
```

- 你只拿得到 `3`，碰不到内核里那个对象
- 所有操作都是"拿着 3 号求内核办事"：`recv(3, ...)`、`send(3, ...)`、`close(3)`
- `0/1/2` 已被占用：标准输入 / 标准输出 / 标准错误

**关键推论**：`close(3)` 之后，3 号可能被下一个 `socket()` 拿走。
所以业务主键不能用 fd（见 `chat::SessionId` 的注释）。

---

## 2. recv 和 send 在搬什么

```
       网络 ──► 内核接收缓冲区 ──► recv ──► 你的 buf
                 (内核地盘)                  (你的地盘)

       你的 buf ──► send ──► 内核发送缓冲区 ──► 网络
```

| 操作 | 方向 | 你控制的部分 | 你控制不了的部分 |
|---|---|---|---|
| `recv` | 内核 → 你 | 最多要多少 | 实际给多少 |
| `send` | 你 → 内核 | 想给多少 | 内核实际收下多少 |

**`send` 的返回值是"收下了多少字节"，不是"成功/失败"。**
内核发送缓冲区满了，它只收一部分，剩下的必须由你重试——这就是
`Connection::send` 里"快路径 + 写缓冲"存在的原因。

---

## 3. 三种返回值

`recv` 的返回值只有三种情况：

| 返回值 | 含义 | 处理 |
|---|---|---|
| `> 0` | 实际搬了多少字节 | 存起来，继续读 |
| `0` | 对端**正常关闭**（发了 FIN） | 关闭连接，这不是错误 |
| `-1` | 出错了，去看 `errno` | 见下 |

---

## 4. errno 是什么

**一个"公共格子"**，不是你声明的变量。`#include <cerrno>` 之后直接用。

```
你的代码 recv(...)
   └─► libc 包装函数
          └─► 内核：失败时返回 -1，并把错误码放进寄存器
   └─► 包装函数把错误码写进 errno，再把 -1 返回给你
```

**重要**：`errno` 只有在对系统调用返回 `-1` 的**当下**才有意义。
它会被后续任何系统调用覆盖。所以要立刻读，或者先存下来：

```cpp
ssize_t n = recv(fd, buf, len, 0);
int saved = errno;          // 先存
if (n < 0 && saved == EAGAIN) { ... }
```

---

## 5. EAGAIN：不是错误，是"现在没有"

| 操作 | `EAGAIN` 的意思 |
|---|---|
| `recv` | 接收缓冲区空了 |
| `send` | 发送缓冲区满了 |
| `accept` | 没有待处理的新连接 |

**它只会出现在非阻塞 fd 上。** 阻塞 fd 遇到"没数据"时会直接睡住，
永远不会返回 `EAGAIN`。

`EWOULDBLOCK` 在 Linux 上和 `EAGAIN` 是同一个值（11），历史上是两派
Unix 的叫法，所以代码里两个都判断。

---

## 6. 阻塞 vs 非阻塞

| | 阻塞（socket 默认） | 非阻塞（本项目） |
|---|---|---|
| 缓冲区空时 `recv` | 睡住，直到有数据 | 立刻返回 `-1` / `EAGAIN` |
| 后果 | **整个事件循环停摆** | 事件循环继续转 |

一个客户端发了半个帧，就足以让阻塞模式的服务器对**所有**用户失去响应。

所以 `set_nonblocking(fd)` 不是优化，是**正确性要求**：
`Acceptor` 对每个新连接调用它，`Connection` 的读循环建立在它之上。

## 7. epoll 在做什么

```
epoll_create1  → 建一张"关注列表"
epoll_ctl      → 往列表里增删改：我关心这个 fd 的"可读"
epoll_wait     → 阻塞等待，返回"就绪的那几个"
```

**它不是轮询。** 内核在数据到达时直接把 fd 标成就绪，`epoll_wait` 只需
要把就绪队列交出来——所以 1 万个连接和 10 个连接的等待成本几乎一样。
这就是它比"每连接一个线程"强的地方。

常用的三个事件位：

| 事件 | 含义 | 什么时候用 |
|---|---|---|
| `EPOLLIN` | 可读 | 一直关注 |
| `EPOLLOUT` | 可写 | **只有积压时才关注**，否则每次可写都唤醒，白烧 CPU |
| `EPOLLRDHUP` | 对端关了写方向 | 用来及时发现半关闭 |

---

## 8. 一张图串起来

```
    网络包到达
        ↓
   内核接收缓冲区有数据
        ↓
   epoll_wait 返回 "fd 可读"
        ↓
   Connection::handle_read()
        ↓
   for(;;) { recv → 有数据就继续；EAGAIN 就退出 }
        ↓
   数据进了 Buffer
        ↓
   上层用 try_decode 切出完整的帧
```

每一步的细节都在对应文件的注释里。这份文档只负责让你**看懂那些注释在说什么**。
